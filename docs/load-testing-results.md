# 쿠폰 발급 부하테스트 실험 기록

실행 방법과 지표의 의미는 [부하테스트 안내](load-testing.md)에 있다. 이 문서는 **실행별 사실 → 원인 가설 → 변경 → 재측정 결과**를 누적한다.
성능 저하의 최초 원인과 그 결과로 발생한 장애를 구분하고, 재측정 전에는 원인을 확정하지 않는다.

현재 기준 결과(2026-09-27): 이벤트와 캠페인 상태를 각각 조회하던 발급 경로를 JOIN 한 번으로 합친 [실행 013](#실행-013--2026-09-27-이벤트캠페인-join-적용-jar-실행)은 최대 500 RPS에서 발급 p95 221.36ms, DB 불일치 0을 기록했다. 같은 JAR 실행 방식으로 JOIN 미적용 기준을 다시 측정한 [실행 014](#실행-014--2026-09-27-join-미적용-jar-기준-실행)과 비교하면 전체 p95는 546.68ms에서 221.36ms로 59.5% 낮았다. 단, 각 구현 1회씩의 비교이므로 운영 환경의 확정 용량이나 모든 실행에서 같은 개선율을 뜻하지 않는다. 아래에는 실패 실행도 삭제하지 않고 시간순으로 남겼다.

## 기록 원칙

- 실행마다 날짜·코드/시나리오 버전·앱/DB/k6 위치·재고/사용자·부하 설정을 적는다. 바꾼 항목은 이전 실행과 구분한다.
- `http_reqs`에는 사전 연결 확인 요청도 포함될 수 있으므로 발급 요청은 `iterations`와 발급 전용 지표를 사용한다. 예정·실행·누락 요청을 나누어 기록한다.
- HTTP 201 횟수와 DB의 신규 쿠폰 수를 구분한다. 동일 사용자 재요청 시나리오에서는 멱등 201이 포함될 수 있다.
- 성능 기준 통과, DB 정합성, 전체 재고 소진을 별도로 판정한다. 일부만 발급된 실행의 정합성 0건은 최대 부하에서 안전하다는 증명이 아니다.
- 재현 실험에서는 k6 출력·앱 로그·Hikari 지표·MySQL 상태를 같은 시간축으로 보관한다. 개인정보와 DB 비밀번호는 기록하지 않는다.
- 코드나 설정을 개선했다면 다음 실행에서 같은 환경·부하로 비교하고, 실제로 관찰된 차이만 결론으로 적는다.

### 확인된 징후와 아직 확인되지 않은 원인

1. 약 15~16초 지점 이후 완료 요청이 사실상 멈췄고, 이후 600 VU 상한에 도달했다. 요청 타임아웃과 누락이 이어졌다.
2. 앱 로그에 `HikariPool-1 - Connection is not available, request timed out after 30001ms`가 기록됐다. 지표 조회 시 연결 `total=10, active=10, idle=0, pending=200`이었다. **DB 연결 확보 실패는 확인된 직접 장애 징후**다.
3. 그 10개 연결을 오래 점유한 최초 원인은 아직 확정하지 못했다. DB 잠금 대기, 긴 트랜잭션, 앱에서의 연결 반환 지연 등을 구분할 동시간대 MySQL 상태·스레드 덤프가 부족하다. 부하 종료 후 `SHOW FULL PROCESSLIST`에서는 연결이 `Sleep`이었지만, 이를 부하 중 DB가 유휴 상태였다는 증거로 사용할 수 없다.
4. 코드에서 발급 요청은 [사전 중복 조회](../src/main/java/io/github/minhyeok/coupon_prac/v1/coupon/service/CouponService.java)를 한 다음 독립 쓰기 트랜잭션에서 사용자 확인, 한도 생성·증가, `SKIP LOCKED` 재고 선점, 쿠폰 저장을 한다. 재고 조회에는 `(event_id, status, sequence_no)` 인덱스가 있다. 어느 단계가 정체됐는지는 계측으로 확인해야 한다.
5. 클라이언트 타임아웃은 서버 요청 중단을 보장하지 않는다. 현행 k6 `teardown()`은 서버가 조용해졌는지 확인하지 않고 DB를 검증·삭제한다. 따라서 1,098장과 불일치 0건은 그 순간의 값이다. 종료 후에도 앱에서 예외 로그가 계속 나왔으므로 향후에는 삭제 전에 서버 측 처리가 끝났음을 확인해야 한다.

**현재 결론:** `SKIP LOCKED` 실패나 MySQL 자체의 처리 한계, `REQUIRES_NEW` 교착, 연결 누수를 단정할 근거는 없다. 연결 풀 크기만 늘리는 변경도 최초 점유 원인을 모르면 문제를 늦춰 보이게 할 수 있다. 재요청 제거 역시 이 장애의 해결책으로 검증되지 않았다.

## 진단 절차 변경 — 실행 002 전

- k6의 `K6_DEFER_VERIFICATION=true`를 추가했다. 이 옵션의 발급 실행은 자동 검증·삭제를 하지 않아 장애 시 테스트 데이터를 보존한다.
- 같은 스크립트의 `K6_MODE=verify`는 실행 ID의 데이터만 읽어 정합성을 검증한다. 앱을 중지해 진행 중인 요청이 없어진 뒤 실행한다. `K6_MODE=cleanup`은 기존대로 별도 명시적 쓰기 허용 후 실행한다.
- 기본 자동 정리 모드는 변경하지 않았다. 보류 모드의 k6 성공은 **성능 지표만** 뜻하며 DB 정합성 완료를 뜻하지 않는다.
- 다음 진단은 격리된 Docker MySQL 8.4, 호스트의 앱 JAR, Docker k6를 사용한다. 이벤트 10개·재고 5,000장·고유 사용자 4,000명으로 고정하고, 40초 램프의 최대 RPS만 바꾼다. 부분 부하에서는 `K6_REQUIRE_SOLD_OUT=false`다.
- 낮은 RPS부터 실행하며 정체가 발생하면 **부하 진행 중** Hikari 지표·스레드 덤프·MySQL 잠금 대기를 수집한다. 실행마다 요청 수·지연·DB 정합성·정리 결과를 아래에 별도 기록한다.

## 후속 코드 단순화 — 2026-09-26, 기본 `@Transactional`로 통합

실행 010 이후 학습·유지보수 목적에서 `CouponService.issue()`의 `TransactionTemplate`, `NOT_SUPPORTED`, `REQUIRES_NEW`,
`READ_COMMITTED` 설정을 제거했다. 기존 쿠폰 조회부터 한도·재고·사용자 쿠폰 변경까지 `@Transactional` 하나에서 실행한다.

- HTTP 컨트롤러에서 직접 호출하면 서비스가 트랜잭션 하나와 DB 연결 하나를 연다.
- 상위 서비스가 트랜잭션을 열어 호출하면 발급도 그 트랜잭션에 참여한다. 따라서 상위 작업이 롤백되면 발급도 롤백된다.
- `SKIP LOCKED`가 빈 결과를 반환하면 현재 트랜잭션은 `INVENTORY_BUSY`를 반환한다. 별도 트랜잭션을 열어 품절 여부를 재조회하지 않는다.
- 한도 증가 전 AVAILABLE 재고가 없음을 확인한 경우에는 이전과 같이 `COUPON_SOLD_OUT`을 반환한다.
- MySQL 기본 `REPEATABLE_READ`에서 동시 동일 요청의 오래된 읽기 스냅샷을 피하기 위해, 첫 일반 조회 전에 항상 존재하는 사용자 행을 `SELECT ... FOR UPDATE`로 잠근다. 같은 사용자는 직렬화되지만 서로 다른 사용자는 서로 막지 않으므로, `READ_COMMITTED` 설정 없이도 중복 INSERT를 막는다.

실행 010의 성능 수치는 이 단순화 **전** 구현의 측정값이다. 이 변경은 통합 테스트로 트랜잭션 참여·롤백과 기존 발급 규칙을 확인했다.

지연 요인이지만, 현재 500 RPS에서 반복되는 근본 병목은 10개 연결 풀을 한계까지 사용하는 발급 흐름**이다.

현 발급 흐름은 요청 하나가 사용자 잠금, 기존 쿠폰 확인, 이벤트·캠페인 확인, AVAILABLE 재고 선조회, 일일 한도 UPSERT,
재고 `SKIP LOCKED` 선점, 사용자 쿠폰 INSERT, 재고 상태 UPDATE와 COMMIT을 순서대로 수행한다. 이전 구현도 기존 쿠폰을
트랜잭션 밖과 안에서 각각 한 번씩 확인했다. 달라진 점은 현재 구현이 **모든 요청에** AVAILABLE 재고 선조회를 하나 더 수행하고,
사용자 조회를 `SELECT ... FOR UPDATE`로 바꾸었으며, 이전에는 트랜잭션 밖에서 끝났던 첫 쿠폰 조회도 같은 발급 트랜잭션의
연결 점유 시간 안으로 넣었다는 것이다. 이 추가 조회·잠금·점유 범위는 올바른 규칙을 위한 비용이지만, 풀 여유가 없는 500 RPS에서는
처리량 경계에 도달하게 만든다.

`REPEATABLE_READ`에서는 비유일 인덱스 범위의 잠금 읽기에 next-key/gap 잠금이 사용될 수 있어 실행 011의 재고 잠금
경합 가능성은 높아진다. 그러나 실행 012가 더 느렸으므로 `READ_COMMITTED` 전환만으로 해결된다고 결론 내릴 수 없다.
MySQL의 격리 수준별 잠금 동작은 [MySQL 공식 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)와
[잠금 설정 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-locks-set.html)를 참고한다.

다음 개선 실험은 코드를 바로 바꾸기보다, DB를 같은 초기 상태로 재기동한 뒤 각 후보를 최소 3회 반복해 중앙값을 비교한다.
후보는 (1) 이 시나리오에 필요한 멱등성 보장을 유지하면서 불필요한 재조회 수를 줄이는 방법, (2) 커넥션 풀 크기와 DB 동시 처리량을
함께 조절하는 방법, (3) 재고 선점 SQL의 인덱스·잠금 범위를 재검증하는 방법이다. 풀 크기만 늘리는 것은 DB가 감당할 수 있는지
확인하지 않으면 대기 위치만 MySQL로 옮길 수 있으므로 단독 개선으로 확정하지 않는다.

### 이번 변경의 코드 수준 의미

변경 전 발급 경로는 다음처럼 앱과 DB 사이를 두 번 왕복했다.

```java
CouponEvent event = events.findById(command.eventId()).orElseThrow();
Campaign campaign = campaigns.findById(event.getCampaignId()).orElseThrow();
if (!event.isIssuableAt(now) || !campaign.allowsIssuance()) {
    throw new CouponException(CouponErrorCode.EVENT_NOT_ISSUABLE);
}
```

변경 후에는 필요한 네 값만 projection으로 받고, 한 쿼리 결과로 같은 판단을 한다.

```java
CouponEventIssuanceContext context = events.findIssuanceContextById(command.eventId())
        .orElseThrow(() -> new CouponException(CouponErrorCode.EVENT_NOT_FOUND));
if (!context.isIssuableAt(now)) {
    throw new CouponException(CouponErrorCode.EVENT_NOT_ISSUABLE);
}
```

즉, 한 요청에서 쿠폰 이벤트 행과 연결된 캠페인 행을 MySQL 내부에서 합친 뒤 앱에는 필요한 열만 한 번 보낸다. 이는 이벤트·캠페인
발급 판단에 한정한 최적화다. 사용자 잠금, 일일 한도, 재고 선점과 사용자 쿠폰 저장의 규칙·트랜잭션 순서는 바꾸지 않았다.

이번 수치는 각 구현을 한 번씩 실행한 결과다. 다음 성능 판단에서는 두 구현을 각각 최소 세 번 반복하고 p95의 중앙값을 비교해야
우연한 JVM 워밍업·OS 스케줄링·DB 상태 차이를 더 줄일 수 있다. 그 전까지는 **이 환경에서 JOIN 적용 실행이 더 빨랐다**고만
결론 내린다.
